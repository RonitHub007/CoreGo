# Understanding the API Flow in Hexagonal Architecture

This document is a guide for developers new to this codebase. It explains how a single HTTP request flows through the various layers of our Hexagonal Architecture (Ports and Adapters). 

We will trace the journey of a `POST /books` request from the moment it hits the server until it is saved in the database.

---

## The Mental Model: Outside-In

In Hexagonal Architecture, dependencies always point **inward**.
1. **Adapters (Outside)**: These interact with the outside world (HTTP requests, Databases).
2. **Ports (Boundary)**: These are Go `interfaces` that act as gateways between the Adapters and the Core.
3. **Core (Inside)**: This contains the pure business logic and Domain models. It has zero knowledge of HTTP or Databases.

---

## The Journey of `POST /books`

### Step 1: The Entry Point and Wiring
**File:** `cmd/api/main.go` -> `internal/server/server.go`

When the application starts, the `Server` struct acts as the master container. It connects to the Postgres database, initializes the Logger, and performs **Dependency Injection**.

It wires the layers together like this:
```go
// 1. Create the Outbound Adapter (Database)
bookRepo := postgres.NewBookRepository(db, zapLogger)

// 2. Inject it into the Core Service (Business Logic)
bookService := services.NewBookService(bookRepo, zapLogger)

// 3. Inject the Core Service into the Inbound Adapter (HTTP Handler)
bookHandler := http.NewBookHandler(bookService, zapLogger)
```
Finally, it tells the Gin router that any `POST` request to `/books` should be routed to `bookHandler.AddBook`.

---

### Step 2: The Primary Adapter (Inbound)
**File:** `internal/adapters/handler/http/book_handler.go`

A user sends a JSON payload to `POST /books`. The request hits the `AddBook` method in the HTTP Handler.

**Responsibilities here:**
1. Read the HTTP request body.
2. Unmarshal the raw JSON into our pure `domain.Book` struct.
3. If the JSON is invalid, return a `400 Bad Request` immediately.
4. If valid, pass the `domain.Book` to the Core Service via the **Primary Port**.

*Note: The Handler knows about HTTP status codes and JSON, but it doesn't know how the book is validated or saved.*

---

### Step 3: The Primary Port (The Gateway)
**File:** `internal/core/ports/service.go`

The Handler doesn't talk directly to the `bookService` implementation. It talks to the `BookService` **interface**. This boundary ensures that the HTTP layer and the Core layer are decoupled.

---

### Step 4: The Core Service (Business Logic)
**File:** `internal/core/services/book_service.go`

The Core Service receives the pure `domain.Book` from the Handler.

**Responsibilities here:**
1. Enforce business rules (e.g., "A book must have a Title and an ISBN").
2. If validation fails, return a generic Go `error` (not an HTTP error).
3. If validation passes, ask the Database to save the book via the **Secondary Port**.

*Note: The Service knows the business rules, but it has no idea that the request came from Gin, nor does it know that the database is Postgres.*

---

### Step 5: The Secondary Port (The Outbound Gateway)
**File:** `internal/core/ports/repository.go`

The Service needs to save the book, so it calls `s.repo.CreateBook(book)`. The `repo` is the `BookRepository` **interface**. This interface guarantees that whoever implements it will know how to save a `domain.Book`.

---

### Step 6: The Secondary Adapter (Outbound)
**File:** `internal/adapters/repository/postgres/book_repo.go`

This is where the rubber meets the road. The Postgres Adapter receives the pure `domain.Book`.

**Responsibilities here:**
1. Convert the pure `domain.Book` into a `postgres.BookDBModel`. (The DB Model contains GORM specific tags like `gorm:"primaryKey"`).
2. Execute the actual SQL query using GORM (`db.Create(&dbModel)`).
3. Update the `domain.Book` with any fields generated by the database (like the auto-incrementing `ID` or `CreatedAt` timestamp).
4. Return any database connection errors back to the Service.

---

## Summary of Data Flow

1. **Client** sends raw JSON.
2. **HTTP Adapter** converts JSON -> `domain.Book`.
3. **Core Service** validates `domain.Book`.
4. **Postgres Adapter** converts `domain.Book` -> `postgres.BookDBModel`.
5. **Database** saves the record.

Because of this strict translation and isolation, you can safely modify your Database schema without ever breaking your HTTP handlers, and vice versa!
